# Auto Service AI Triage

API-сервис для первичной обработки обращений автосервиса. Он классифицирует
сообщение клиента, готовит черновик ответа, определяет необходимость передачи
обращения оператору и сохраняет историю обработки. Локально используется SQLite,
а для бесплатного публичного развёртывания можно включить совместимую базу Turso.

## Возможности

- приём обращений через `POST /triage`;
- четыре категории: `billing`, `support`, `complaint`, `other`;
- структурированный JSON-ответ языковой модели;
- оценка уверенности: `high`, `medium`, `low`;
- передача сложных случаев оператору через `escalate`;
- валидация входных данных и ответа модели;
- ограничение числа запросов на `client_id`;
- журнал обращений и результатов в SQLite или Turso;
- безопасный резервный ответ при недоступности LLM;
- локальный запуск и запуск через Docker Compose.

## Как работает сервис

```text
Клиент → FastAPI → валидация → ProxyAPI → проверка JSON → хранилище → ответ
                              ↘ ошибка → fallback → хранилище → ответ
```

Языковая модель получает только текст обращения. Значения `client_id`, ключ
ProxyAPI и содержимое базы данных ей не передаются. Модель настраивается через
переменную `LLM_MODEL`, а адрес API — через `PROXYAPI_BASE_URL`.

## Контракт API

### Запрос

```http
POST /triage
Content-Type: application/json
```

```json
{
  "text": "После ремонта снова появился стук в подвеске.",
  "channel": "chat",
  "client_id": "client-001"
}
```

- `text` — обязательная строка длиной от 1 до 2000 символов;
- `channel` — `email`, `form` или `chat`;
- `client_id` — идентификатор клиента.

### Ответ

```json
{
  "category": "complaint",
  "draft_reply": "Передадим обращение мастеру для повторной проверки.",
  "confidence": "high",
  "escalate": true
}
```

- `category` — `billing`, `support`, `complaint` или `other`;
- `draft_reply` — от одного до шести предложений;
- `confidence` — `high`, `medium` или `low`;
- `escalate` — необходимость передать обращение оператору.

Интерактивная документация после запуска доступна по адресу
`http://127.0.0.1:8000/docs`.

## Публичная версия

- API: `https://auto-service-ai-triage.onrender.com`
- Swagger UI: `https://auto-service-ai-triage.onrender.com/docs`
- проверка состояния: `https://auto-service-ai-triage.onrender.com/health`

Приложение развёрнуто на бесплатном экземпляре Render, поэтому после периода
бездействия первый запрос может выполняться около минуты. История обращений
хранится отдельно в Turso и не теряется при остановке или перезапуске контейнера.

### Ограничения учебной демонстрации

Публичная версия предназначена только для искусственных демонстрационных
обращений. В ней нельзя указывать реальные ФИО, телефоны, адреса, номера
автомобилей и другие сведения, по которым можно определить человека.

Такое ограничение принято намеренно: Render и Turso размещают компоненты проекта
на иностранных серверах, а обработка и трансграничная передача реальных
персональных данных требуют соблюдения Федерального закона № 152-ФЗ «О
персональных данных». Реальные персональные данные здесь вообще не
обрабатываются, поэтому в рамках учебной демонстрации требования № 152-ФЗ не
нарушаются: все записи вымышлены и не относятся к реальным людям.

Цель развёртывания — протестировать бесплатную публикацию API и работу
SQL-хранилища: создание записей, их чтение и сохранение после остановки или
перезапуска контейнера. При подготовке проекта не удалось найти подходящий
бесплатный российский сервис, одновременно предоставляющий публичный хостинг и
постоянное SQLite-совместимое хранилище, поэтому для учебного эксперимента были
выбраны Render и Turso. Для реальной эксплуатации необходимо отдельно
спроектировать хранение и защиту персональных данных.

### Автоматическая проверка и публикация

При отправке изменений в GitHub workflow сначала запускает тесты, а после их
успешного завершения проверяет сборку Docker-образа. Render ожидает успешного
результата GitHub Actions и только затем автоматически развёртывает новую версию
из ветки `main`. Изменения только в `README.md` исключены фильтром Render и не
запускают лишнюю пересборку приложения.

### Резервное копирование

Turso автоматически поддерживает восстановление базы на момент времени, а
workflow `Database backup` дополнительно каждый день по расписанию, не раньше
06:17 по московскому времени, синхронизирует удалённую базу в файл SQLite.
Запланированные workflow GitHub могут запускаться с задержкой. Перед сохранением
workflow выполняет `PRAGMA quick_check`, проверяет наличие таблицы `tickets` и
выводит число записей. Проверенная копия сохраняется в GitHub Actions как
артефакт на 14 дней. Workflow также можно запустить вручную через вкладку
`Actions`.

Для подключения используются секреты репозитория `TURSO_DATABASE_URL` и
`TURSO_AUTH_TOKEN`. Они передаются только выполняющемуся workflow и не входят в
исходный код или резервную копию. Поскольку репозиторий публичный, скачать
артефакт может пользователь с доступом к его содержимому; поэтому этот учебный
механизм предназначен исключительно для базы с вымышленными демонстрационными
данными и не подходит для хранения реальных персональных данных.

## Настройка

Создайте `.env` на основе `.env.example`:

```env
PROXYAPI_KEY=
PROXYAPI_BASE_URL=https://api.proxyapi.ru/v1
LLM_MODEL=gpt-4o-mini
LLM_TEMPERATURE=0.2
LLM_TIMEOUT_SECONDS=30
DATABASE_BACKEND=sqlite
DATABASE_PATH=data/triage.db
TURSO_DATABASE_URL=
TURSO_AUTH_TOKEN=
REQUESTS_PER_MINUTE=10
USE_LLM=true
```

Укажите ключ ProxyAPI только в локальном `.env`. Этот файл исключён из Git и
контекста Docker-сборки.

По умолчанию `DATABASE_BACKEND=sqlite`, поэтому для локального запуска Turso не
нужна. В публичном окружении установите `DATABASE_BACKEND=turso`, а также добавьте
выданные Turso значения `TURSO_DATABASE_URL` и `TURSO_AUTH_TOKEN`. Если URL или
токен отсутствует, приложение завершит запуск с понятной ошибкой вместо записи во
временный файл контейнера.

## Локальный запуск

Требуется Python 3.12.

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

## Запуск через Docker Compose

```powershell
docker compose up -d --build
```

Проверка состояния:

```powershell
Invoke-RestMethod http://127.0.0.1:8000/health
```

Остановка:

```powershell
docker compose down
```

Каталог `data` подключается к контейнеру как `/app/data`, поэтому SQLite не
удаляется при остановке или пересоздании контейнера.

## Хранилище и журнал обработки

Локальный режим использует обычный файл SQLite `data/triage.db` и полностью
выполняет требование учебного задания. Бесплатные контейнеры Render имеют
временную файловую систему, поэтому в публичном режиме используется Turso —
удалённая SQLite-совместимая база. Структура таблицы и SQL-запросы в обоих режимах
одинаковы.

Таблица `tickets` содержит:

- время обработки;
- `client_id`, канал и исходный текст;
- категорию, уверенность и флаг эскалации;
- черновик ответа;
- тип ошибки, если обращение обработано через резервный сценарий.

В технический лог выводятся только безопасные диагностические данные: идентификатор
клиента, канал, длина текста, номер записи и класс ошибки. Ключ ProxyAPI в лог не
попадает.

## Резервный сценарий при сетевой ошибке

Во время проверки Docker-контейнер один раз не смог определить IP-адрес
`api.proxyapi.ru`. Внешнее соединение не установилось, и HTTP-клиент вернул
`ConnectError`.

Сервис продолжил работу и вернул контролируемый ответ:

```json
{
  "category": "other",
  "draft_reply": "Ваше обращение передано оператору автосервиса. Оператор уточнит информацию и свяжется с вами.",
  "confidence": "low",
  "escalate": true
}
```

В SQLite сохранились исходное обращение, резервный результат и тип ошибки
`ConnectError`. После восстановления DNS повторный запрос получил успешный ответ
ProxyAPI, был классифицирован как `complaint` с `confidence=high` и также сохранился
в журнале. Эта проверка подтверждает, что временная ошибка внешнего сервиса не
приводит к падению API и потере обращения.

## Тестирование

```powershell
python -m pytest -q
```

Офлайн-тесты не обращаются к ProxyAPI и не расходуют баланс. Они проверяют:

- доступность `/health`;
- валидацию пустого текста;
- обработку корректного структурированного результата;
- отклонение неизвестной категории;
- ограничение черновика шестью предложениями;
- fallback и запись ошибки в SQLite;
- проверку конфигурации и записи в Turso без сетевых запросов;
- блокировку лишних запросов и восстановление лимита через минуту.

Текущий локальный результат: `16 passed`.

## Статус

MVP проверен локально, в Docker Compose и в публичном окружении Render. Реальный
публичный запрос успешно обработан через ProxyAPI и сохранён в Turso. Отдельно
проверен резервный сценарий с записью типа ошибки в удалённую базу.
